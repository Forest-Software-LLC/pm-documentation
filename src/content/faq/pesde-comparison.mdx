# How Forest Compares to pesde

[pesde](https://pesde.dev) is a package manager for the Luau language, supporting multiple runtimes (Roblox, Lune, and standalone Luau), with design cues from npm, pnpm, Wally, and Cargo. It is a capable, thoughtfully built tool, and if your work is centered on the Luau toolchain itself, it has features aimed squarely at that audience.

Forest and pesde have different centers of gravity. pesde goes deep on Luau: one language, several runtimes. Forest goes broad across game platforms and deep on registry services: one registry and CLI serving [Roblox](/platforms/roblox/intro) (Luau) and [UEFN](/platforms/uefn/intro) (Verse), with hosted private packages, team management, license enforcement, and a verifiable delivery pipeline built in. This page lays out where each choice shows up in practice.

## At a glance

| Area | pesde | Forest |
|---|---|---|
| Scope | Luau runtimes: Roblox, Lune, standalone Luau | Game platforms: Roblox (Luau) and UEFN (Verse) |
| Registry model | pesde registry, plus Wally and Git repositories as package sources | One hosted registry, with the open-source Wally catalog [mirrored in](/platforms/roblox/mirrored) |
| Private code | Typically via Git repository dependencies | [Hosted private packages](/concepts/private-packages) with per-member access grants; 10 free on every account and Studio |
| Teams | Publishing tied to individual accounts | [Studios](/studios/intro): ranks, roles, per-package permissions, audit logs |
| Licensing | Optional metadata | License required to publish, with a per-version [license safety rating](/concepts/publishing) |
| Manifest surface | Targets, engines, scripts, workspaces, overrides | One `forest.json` with a single `platform` field and a guided CLI |
| Supply-chain trust | Lockfile | Client-verified SHA-256 for every tarball, an [open-source pipeline](/open-source), and signed build provenance |

## Different problems, deliberately

pesde's multi-target model is genuinely useful if you maintain libraries that run under Lune as well as inside Roblox, and its manifest reflects that: targets, engine declarations, scripts, and workspace tooling give library authors a lot of control.

Forest optimizes for a different user: teams shipping games. Each Forest package targets exactly one platform, the CLI walks you through `init` and `publish` with prompts instead of configuration, and versioning is guided (the CLI asks whether a change is a bugfix, feature, or breaking change and bumps SemVer accordingly). The goal is that a developer who has never used a package manager can publish correctly on the first try, and that what they publish is correct by construction: license present, dependencies exactly as recorded in the manifest, integrity hash pinned in every consumer's lockfile.

Neither philosophy is wrong; they serve different rooms. If your team's question is "how do we share and control code across our games and our people," the rest of this page is the comparison that matters.

## A registry with services behind it

Forest's registry is a hosted product, not only an index:

- **[Private packages](/concepts/private-packages)** are built in: mark a package private at publish time and it never appears in search, downloads require an authenticated account with access, and tarballs are served through short-lived signed URLs. No Git submodule wrangling or deploy keys to share internal code.
- **[Studios](/studios/intro)** give teams collective ownership: packages belong to the organization, with ranks, custom roles, per-package permission grants, and an audit log. Members can come and go without orphaning a package.
- **Accounts** are Forest-native with two-factor authentication on every account, managed on the web rather than through a third-party identity.

## Licensing is enforced, not assumed

Forest requires a license (an SPDX identifier or a `LICENSE` file) on every published package, and every version carries a [license safety rating](/concepts/publishing). For commercial teams, an unlicensed dependency is a legal question mark; Forest is designed so that question mark cannot enter the registry in the first place.

## A pipeline you can verify yourself

Every component that touches package bytes on Forest is [open source](/open-source): the CLI, the publish/download gateway, and the CDN worker. A tarball's SHA-256 is its storage key, its URL, and the `integrity` value in your lockfile; the CLI recomputes it on every download and refuses to install on a mismatch. The gateway deploys only from its public repository through GitHub Actions with signed build-provenance attestations. Trust in the registry is checkable, not assumed.

## The existing ecosystem, either way

Both tools took the Wally ecosystem seriously. pesde can consume Wally packages as a dependency source; Forest [mirrors the open-source Wally catalog](/platforms/roblox/mirrored) directly into its registry, unmodified and automatically updated, with authors' scopes reserved for them to claim. On Forest a mirrored package is a normal package: same search, same lockfile, same integrity verification, and no separate source type in your manifest.

## Types and tooling

pesde generates link modules so Luau types flow through `require` without extra tools, and that is a real quality-of-life win over older workflows. Forest reaches the same outcome by a different route: packages install as real ModuleScripts required by instance path, with [relative link modules generated](/platforms/roblox/installing#package-dependencies) only where nesting requires them, so types and requires resolve natively with no additional tooling on either side.

<Callout type="info">
The fastest way to compare is to try both on a real project. Forest's [CLI installs in one command](/forest-cli/install), and `forest i` on any package, mirrored or native, will show you the full manifest, lockfile, and layout in a few minutes.
</Callout>
